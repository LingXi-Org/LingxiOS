# Runtime3.6.0 / native14: public skill delivery

This source prepares3.6.0; it does not publish or deploy the runtime. Native14 requires a separate explicitly drained migration016 from native13. Historical schema013 is immutable, and old rollback015 is incompatible with14. Release integrator must verify the exact CI/reviewed head, immutable artifacts, registry availability, and native upgrade before updating product locks. The development author could not list GitHub package versions: existing credentials returned HTTP403/read:packages. Availability of3.6.0 is unverified; never overwrite an existing version.

Skills opt in using `delivery: { checker }`. Explicit `skills.activate` and the public `ActionContext.activateSkillDelivery({ name, version, hash })` use the same exact native contract, current tenant/principal/run/request and fresh capability checks. The context method is available only during a transactional tool's execute phase. Trusted product save/chart/diagram tools should validate input first, then await it and write the actual artifact using context.database. No direct native ledger SQL or private receipt parsing is needed. Ordinary read/export/examples and unconfigured skills do not create obligations.

The authoring write and new activation share one transaction: invalid/no-effect, thrown errors and cancellation before commit roll both back. Previously committed explicit activation remains pending if a later tool fails. First authoring failure with no prior activation leaves no durable obligation; this API does not claim enforcement of a rolled-back intent. Normal cancellation uncertainty remains authoritative when a COMMIT acknowledgement is lost.

Products provide `verifySkillDelivery` using the public current-request activation projection and context.database. They independently authorize/read the candidate's real artifact, bind product provenance to the current request version and source hash, and decide delivered, pending, or an honest unsupported/failed explanation. A save/readback hash alone is not numerical or semantic quality evidence. Final commit rechecks this decision; candidate-time checks never resolve it. A satisfied envelope cannot claim success after unsupported/failed; an automatic conversion of incorrect model assessments to partial is not promised by the current coverage.

Database-backed capability policies must adopt `CapabilityResolver.resolve(work, context?)` and use context.database throughout nested policy reads. Native conversation/ancestry/current+ancestor policy checks reuse the active transaction, preventing pool reentry. Existing pure one-argument resolvers remain source-compatible. Old unconfigured/unactivated paths are not newly invoked under the final transaction; opting into the new transactional activation path requires the scoped resolver contract.

The typed ActionContext gains the method; external manually constructed ActionContext fixtures must add it or use their explicit fixture cast. Existing runtime callers receive it automatically. No dependency versions, private protocol parsing, keyword activation, model/provider behavior or client rendering changes are introduced.
