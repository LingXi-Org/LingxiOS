# Public skill delivery obligations — before implementation

Base35ac1208 (runtime3.5.8/native13). This upstream draft introduces explicit authoring activation and authoritative delivery verification, not model quality acceptance. No provider/browser or production operations.

- Reference-only loads, examples and exports must never create an authoring obligation. Activation requires an exact current skill name/version/hash plus its existing capabilities; neither model text nor a private action receipt implies activation.
- Durable activation belongs to tenant/run/principal/current request version and authored skill hash/checker. A second tool cell deduplicates; another tenant, superseded revision, cancelled run, stale fence, changed skill or revoked capabilities cannot reuse it. No authoring state in caller-supplied metadata.
- Activation is not delivery. A model cannot resolve its own obligation or forge a product verifier record. The trusted host sees typed activations; absent, duplicate, stale, malformed or oversized decisions fail closed. Outcomes distinguish delivered from unsupported/failed with an honest user-visible explanation, or pending.
- Candidate verification never commits resolution. The final message transaction rechecks the current authoritative decision and binds the recorded resolution to the exact candidate hash. No optimistic candidate decision survives resource/authorization changes. Unresolved authoring cannot be hidden by a partial final; cancellation still terminates safely without a pretend delivery.
- Static obligations/product checks must continue to work; no change to ordinary skills.load or existing unconfigured skills. Opt-in public API additions preserve prior callers. Schema14 is an explicit drained upgrade via016; no automatic DDL, runtime publishing or product lock edit. Historical schema13 remains immutable and rollback015 tests must use that historical schema.
- Inputs, number of activations/decisions and serialized evidence are bounded. No activation can be forged through HTML, keywords, runtime receipts or a model-controlled resolution tool. New state is a dedicated native table with scoped reads and transactional writes.

Targeted checks authored before implementation: exact schema migration and historical guard; public load vs activation and idempotence; current request/fence/cancellation/tenant/capability checks; verifier pending/delivered/unsupported/failed and malformed decisions; final commit revalidation with rollback. Existing harness regressions and compiler are owning compatibility checks. Original product provider failures remain red.

Initial owning tests exposed helper capability projection: separate grants for the same `skills` namespace make `skills.activate` unreachable because authorization picks the first matching namespace. Merge helper methods under one namespace before returning grants; do not expand business permissions. Independent review also identified liveness edges before correction: revoked/missing skill capabilities must forbid a delivered claim but permit a trusted honest unsupported/failed explanation; waiting for input, approval or delegated child work must preserve a pending obligation without resolving it or falsely declaring delivery.

Activation is a native state change, not an external business effect. Its receipt must not satisfy the generic business-action completion gate or an external-delivery obligation. A targeted task.inspect assertion must remain false after activation alone. Generated diagram-box coordinate/size correctness outside the bounded numeric renderer is a separate assigned product defect, not solved by this API or CSS zoom; it remains a subsequent implementation slice.

Before hardening016: a missing schema_version singleton yields SQL NULL, so `<>13` would not reject the invalid source. The upgrade must reject absent provenance as well as wrong versions, without creating the activation table; use a null-safe guard. Add this counterexample to the existing migration check before changing it.
